A regional card acquirer runs 1,500 payment terminals across 600 merchants. Today fraud is caught by a nightly batch and a dead terminal is caught by the merchant phoning in. Fabric Real-Time Intelligence puts both on one event stream: authorisations and device telemetry land in an Eventhouse within seconds, every event resolves to its merchant, store and terminal, and four reflexes fire on patterns instead of on schedules. Then, when the chargebacks arrive 30 to 60 days later, the same platform grades every alert it raised and publishes its own precision.
New in Project 25 Carried from P23 / P24 Behind an open gate Killed 2026-08-17

Producers — the data does not exist until it is generated

There is no supplied source file. Unlike P23 and P24 this project generates from zero, which removes the frozen-control-totals obligation and replaces it with a harder one: the generator is the specification.

Seeded generator

Fixed seed, versioned, byte-reproducible. Proven with diff -rq across two independent runs — not a checksum of the data, which is how P24's determinism trap hid.

Notebook · backfill

90 days of auths, 30 of telemetry, disputes and ground truth. Runs in-capacity, so it survives a closed laptop.

Local Python · live replay

60× real time into the Event Hub-compatible endpoint, for the demo and screenshot window. Both routes share one generator module.

Landing_Manifest.csv

Per-stream row counts, min/max event time, seed, version, injected-episode register. Every downstream count reconciles to it.

▼

Ingest — Eventstream

Two mandatory streams with genuinely different shapes and rhythms; a one-stream demo is thin. Disputes are deliberately not a stream.

ES_auth_events

~60k/day. Amount, MCC, entry mode, response code, issuer BIN, latency, token, geo. The hot path.

ES_terminal_telemetry

15-min heartbeat × 1,500 devices. Uptime, connectivity, battery, firmware, tamper sensor.

ES_fabric_job_events

Real-Time Hub's own job events — the platform watching itself. Nice-to-have; the ops-page bonus.

Disputes are a batch

Chargebacks arrive as a daily file in reality, so they land cold-path and are raised into a KQL table for the grading join. Honest, not convenient.

Hot path — Eventhouse, and KQL as the transformation layer

The single biggest structural difference from P23 and P24: there is no Silver notebook and no Gold notebook. Update policies and materialized views do that work. Spark notebooks ≤ 2 is the anti-drift number, and a third is a contract change.

Raw → update policies

4 raw tables land as delivered. Update policies type, dedupe and route on ingest — the streaming equivalent of Silver, with no orchestration to schedule.

Materialized views ×3

The Gold equivalent. Aggregation maintained by the engine rather than recomputed by a job.

12 KQL functions

The hot path's "measures". Reusable, parameterised, and the same definitions the Real-Time Dashboard binds to.

dim_estate

Merchant → Store → Terminal → Issuer. This is what the killed twin was going to be. Every alert resolves through it; zero orphan terminals is an exit criterion.

Anomaly detection, in-engine

series_decompose_anomalies — reflex 4 compares each issuer BIN against its own baseline. On live series, no data movement, and no fixed threshold to be wrong about.

dq_results · alerts · ground_truth

Three tables that make the pitch checkable: what the rules found, what the reflexes fired, and what was actually injected.

Cold path — the part nobody demos

A thin Lakehouse, kept for three reasons and no longer for a fourth: the twin's mandatory source requirement died with the twin.

Replay store

The generator's output on Delta, so the estate can be rebuilt from empty without re-running against the wire.

Dispute batch landing

Daily chargeback file. Raised into Eventhouse for the grading join.

Hot-vs-cold reconciliation

Does Eventhouse agree with the Lakehouse replay? Row counts and summed amounts. DQ rule 6, and a genuinely new check class for this engine.

The loop that makes this a platform, not a dashboard → A reflex fires in seconds and writes a row to alerts with its maturity cohort. Thirty to sixty days later the chargeback for that authorisation lands in the cold path, joins back to the alert, and grades it. The Alert Precision page publishes precision and recall by cohort — and shows the ungraded cohort as awaiting grading, never as zero. Reflex quality is also measured against ground_truth, so the platform has two independent graders rather than one. Neither P23 nor P24 had an analogue for this.

The maturity cohort — why a 23-day trial can still publish precision

Grading appears to need 30–60 day-old disputes against 23 days of capacity. That conflict is false. The generator's clock is synthetic, so a 90-day backfill already contains matured disputes for its own earlier authorisations. No lag-compression is needed, which means it is not a declared synthetic extension — and the cohort structure is how a real fraud-ops team reports precision anyway.

CohortDispute maturityWhat the Alert Precision page shows
T−90 → T−60Fully maturedPrecision and recall, measurable on day one
T−60 → T−30Partially maturedPrecision with the maturity percentage stated alongside it
T−30 → T, and liveNot yet maturedAwaiting grading — never zero. Reporting precision across an ungraded cohort is the defect this design exists to avoid

Six stream data-quality rules — the new problem class

P24 proved batch data quality: a late file, a restatement, one column of schema drift. Streaming's equivalents are harder, and two of them have no batch analogue at all. Every fault is injected deliberately by the generator, so each rule has something true to find.

#RuleFault modelledP24's batch analogue
1Idempotent dedupe on auth_idAt-least-once delivery replays the same eventDuplicate natural keys
2Out-of-order resolutionA reversal or partial capture arrives before its original authorisationThe _R2 restatement — but harder
3Late arrival past the watermarkA terminal buffers offline, then dumps 40 minutes at onceThe late file
4Device clock skewevent_time vs ingest_time per terminal; the dashboard must declare which it trustsnone
5Payload schema evolutionA 3DS/SCA field appears mid-stream; schema-on-read absorbs it with no redeployThe schema drift
6Hot-vs-cold reconciliationEventhouse vs Lakehouse replay — row counts and summed amountsRow-count reconciliation

Two rules carried from P24 govern all six. "The cell didn't error" is not proof — every silent-tagging rule (1, 2, 3) needs an independent downstream structural check, because P24's resolve_restatements() ran clean and was wrong. And every check needs a floor that "nothing" cannot satisfy — a rule finding no rows must prove it read some.
