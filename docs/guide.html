Catch the fraud while it is happening — then prove you were right

Follow along and you will build a working real-time payments risk platform: ten million events in an event database, four detection rules firing on patterns instead of schedules, a live operator dashboard — and, when the chargebacks arrive two months later, a report that grades every alert the platform raised and publishes its own precision. No prior Fabric experience assumed, and nothing to buy.

Why anyone builds this

Meridian Pay is a card acquirer: it owns the terminals in shops, not the cards in wallets. Two things go wrong constantly, and both are usually found far too late.

The problemHow it usually gets found
Card testingA nightly batch job, the next morning
A compromised terminalA chargeback, six weeks later
A dead terminalThe merchant phones in to ask why they took no money today
An issuer quietly decliningNobody, until the merchant churns

The last one is the interesting case. Nothing is broken — an issuer's approval rate has drifted down two points, which is invisible against a fixed threshold and obvious against that issuer's own baseline.

And the part most demos skip: a fraud platform that raises alerts and never checks them is just an opinion generator. This one grades itself. When the disputes arrive 30 to 60 days later, it goes back over every alert it raised and publishes its own precision — by cohort of how mature the evidence is, never as one blended number.

1

Set up the workspace — and connect Git before you build anything

about 20 min

Everything lives in one Fabric workspace — a project folder in the cloud that holds databases, dashboards and reports side by side.

  1. Sign in at app.fabric.microsoft.com with your work or school account.
  2. Workspaces → New workspace. Call it something like Real-Time Payment Risk.
  3. Under Advanced, set the licence mode to your Trial capacity.
  4. Workspace settings → Git integration. Connect it to a repository and branch now.
Why Git first, before a single item exists? Because from this point every item you create lands on disk as a definition file the moment you save it. That is a continuous export mechanism you get for free, and it is the difference between a project you can rebuild and a project that lives only inside a trial that expires.
A Fabric trial needs a work or school account. A personal Microsoft account cannot activate one — not with a different email, not by paying. If you do not have one, that is step zero, and there is nothing to debug.
Set a calendar reminder three days before the trial ends. When it lapses the workspace stops working and everything inside becomes unreachable. Export at checkpoints, not at the end.
The Git provider wants a PAT, not the OAuth flow you expect
The connect dialog looks like it will bounce you through a sign-in. It will not — it wants a personal access token pasted in. Generate one with repo scope before you start the dialog.
2

Generate the estate and the events

about 2 h

A payments platform needs payments. This build generates its own — 1,500 terminals across 927 stores and 600 merchants, and about ten million events over ninety days.

Why generate rather than download a dataset? Because the interesting part of this project is grading the alerts, and you cannot grade an alert without knowing which events were genuinely fraudulent. The generator plants a known set of episodes — 137 of them — and that register becomes the answer key everything downstream is measured against.

Clone the repo, then:

pip install -r 01_Source/requirements.txt
python -m generator.backfill --seed 250817 --out ./output

It writes Parquet feeds plus a Landing_Manifest.csv — a row per file with its row count, so every downstream number has something to reconcile against.

The generator deliberately injects four things a clean dataset would not have:

What it injectsWhy it earns its place
Duplicate rows — 21,462 auth, appended at the end of the frame unshuffled Gives the deduplication layer something real to remove, and — as it turns out — exposes a Kusto behaviour that would otherwise have shipped silently. See step 4
Out-of-order reversals and late arrivals past the watermark Gives the data-quality rules something to detect that is not just "a column is null"
Device clock skew on every terminal Forces an explicit decision about which timestamp is authoritative
A schema cutover partway through the window Real estates do not have one payload shape forever
Seed it, version it, and prove it. Run the generator twice into different folders and diff -rq them. If they differ, every number you publish later is unreproducible and you will not find out until someone asks. This project's second run produced an identical manifest checksum from a completely fresh container — which is a stronger proof than the first run's own self-check.
3

Create the Eventhouse and land the backfill

about 1–2 h

An Eventhouse is Fabric's store for event data. Inside it is a KQL database — a column store built for "what happened in the last ten minutes" over billions of rows.

  1. New item → Eventhouse. Call it EH_MeridianPay.
  2. Create the raw and staging tables from kql/00_raw_and_staging_tables.kql.
  3. Load the backfill with the notebook in notebooks/, then reconcile every table against the manifest.
Run your gates against the empty database first. Several questions — is the capacity right, can this SKU create the items you need, does the metrics app even see this workspace — are cheaper to answer before data exists, and a gate that genuinely needs data should say so in its own plan.
Why one notebook and not three
The instinct on Fabric is Bronze/Silver/Gold notebooks. This build caps itself at two Spark notebooks in the contract and uses one, because the transformation layer is going to be KQL update policies instead — see step 4. Writing the cap down as a number is what stops the drift; a third notebook then has to be argued for in writing.
4

Build the transformation layer in KQL — no notebooks

about 3 h

This is the step that makes the build different. Instead of notebooks reading Bronze and writing Silver, the transformation runs inside the database, as rows arrive.

PieceWhat it does
Update policyA query that runs automatically on every ingest, writing the result into a curated table. This is your Silver layer
Materialized viewAn always-current aggregate maintained by the engine. This is your Gold layer
FunctionsNamed queries — the detection rules and the data-quality checks live here
An update policy deduplicates PER INGESTED BATCH, never across the table. summarize arg_max(...) by key only removes duplicates whose original arrived in the same batch. In this build the generator appends duplicates at the end of the frame, so at 250,000-row batches they all landed in the final batch while their originals sat across the preceding 5.36 million rows. 3,414 of 21,477 were caught. Nothing errored. Every command succeeded, the policy ran clean, and the tables filled with a 0.4% inflation nobody would have noticed.
How it was caught, and why that matters more than the bug. The reconciliation compared curated row counts against independently measured distinct-key counts read off the generated Parquet — not against raw row counts. Had it compared to raw, all sixteen tables would have read OK and the defect would have reached the semantic model. Reconcile against a number the pipeline did not produce.

The fix is a staged global dedupe: take_any(*) into a staging table, verify by count, swap it in, drop the staging table.

// take_any(*), NOT arg_max(key, *) -- the latter must hold all 19 columns per
// group across 5.38m rows and dies with LowMemoryCondition. The injected duplicates
// are byte-identical, so take_any returns the same row and is bounded in memory.
.set-or-replace auth_curated_stg <| auth_curated | summarize take_any(*) by auth_id
Kusto refuses .set-or-replace when the source query reads the destination
ClientAdminCommandFromQueryBadRequestException. Wrapping the query in a function does not help — Kusto resolves the body. Stage into a second table and swap.
The Queryset ends a statement at the first semicolon
In a multi-let function body the first ; is inside the body, so the editor splits the statement in the wrong place. Six of nineteen functions in this build were silently never created that way — found by noticing an alphabetical gap in .show functions, not by any error. Select such blocks by hand and run the selection.
5

Six stream data-quality rules

about 1 h

Each rule counts something, records the count, and states a floor it must clear. The results go into a table, because a check whose result nobody stored did not happen.

RuleWhat it proves
Idempotent dedupeEvery duplicate key was removed — and the count reconciles to the injection register
Out-of-order reversal resolutionA reversal arriving before its authorisation still resolves correctly
Late arrival past watermarkLate data is counted rather than silently dropped
Device clock skewEvery terminal's skew is measured, not assumed
Payload schema evolutionThe cutover is visible and quantified
Hot vs cold reconciliationThe streaming path and the batch path agree
Give a rule a floor that equality can fail. The hot-vs-cold rule knows the exact gap it should find — 50 rows excluded from each of two feeds, by design — so its floor is equality, not greater than zero. A floor of "> 0" passes for the wrong reason more often than it fails for the right one.
Leave a check null rather than inventing one. Three of the six rules have no independent downstream artefact to check against. Their independent_check_passed column is null, and that is recorded as a deliberate decision. Fabricating a second opinion would have been worse than an honest gap.
Six rules in one query will exhaust the capacity's memory
The first version packed all six into a single statement with ~20 toscalar() scans over 5.4 million rows. Split them into six independent statements.
6

Four reflexes, and Activator

about 2 h

A reflex here is a KQL function that returns the rows meeting a detection rule. Activator is the Fabric item that runs one on a schedule and does something when it fires — an email, a Teams message, a webhook.

ReflexWhat it looks for
1 · Card testing burstA spike of small declining authorisations on one terminal
2 · Terminal compromiseTamper telemetry alongside an abnormal decline pattern
3 · Terminal darkA terminal silent for 20+ minutes while its store is trading
4 · Issuer degradationAn issuer's approval rate below its own decomposed baseline
Reflex 4 is the one worth copying. A fixed approval-rate threshold is useless because issuers differ structurally — 92% is healthy for one BIN and alarming for another. series_decompose_anomalies at sigma 2.5, hourly, gives every issuer its own baseline and flags departures from it. And an hour with no traffic is written as a gap, not as a 0% approval rate — a zero there would be a fabricated outage.
An arg_max materialized view cannot time-travel. Reflex 3 originally read a "last seen per terminal" MV. That view has already collapsed to one row per key before any query sees it, so no where clause can ask what it looked like last Tuesday — which means the reflex cannot be graded against a historical backfill at all. The fix is one line: read the curated table directly and filter trusted_time <= ref_time before the max(). Worth knowing before you choose the MV, not three phases later.
7

The Real-Time Dashboard — generated from files, not drawn

about 2 h

Three pages: estate health, fraud watch, issuer performance. The dashboard is generated from a Python spec plus one .kql file per tile, and imported as JSON.

Why not just build it in the designer? Because you will change it fifteen times. Every tile query in this build lives in its own file, a checker resolves every identifier in every query against the actual database schema before anything is imported, and the JSON is rebuilt from source. A fix made in the designer is lost on the next build — so the rule is simply never to make one.
python rtd/build_rtd_json.py --skeleton skeleton.json --out RTD_MeridianPay.json
# then: open the dashboard -> Manage -> Replace with file
Export an empty dashboard first and build from its envelope. The $schema, the schema version and the data-source id are not documented anywhere — take them from a file the service itself produced rather than guessing.
Deneb does not run in a Real-Time Dashboard
Two tiles were specified as Deneb visuals. RTD has its own native types — use anomalychart and heatmap instead.
There is a minimum tile size, and a point budget
Tiles smaller than 9×7 are rejected outright — consolidate several stats into one multistat. And a decomposition tile has a point budget that is easy to blow: series_decompose_anomalies returns three series, so 24 issuers × ~2,120 hourly buckets became 152,640 points against a 50,000 maximum over a 90-day window. Do not widen the step to make the error go away — that silently turns an hourly analysis into a different one. Declare the tile short-window and say which reference window is its evidence window.
8

Make the data readable by Power BI — and load the measures

about 2 h

A Direct Lake model reads the Delta files directly. No import, no refresh schedule, and — in this build — no Gold notebook underneath it.

  1. In the KQL database, turn on OneLake availability. The Eventhouse starts mirroring every table into Delta.
  2. Create a Lakehouse and add a shortcut to each table you want in the model.
  3. Build the semantic model on the Lakehouse, then load measures over XMLA.
Do not .set-or-replace a table whose OneLake mirror is already live. OneLake availability mirrors ingestion; an extent-level replace is not guaranteed to propagate. This build did exactly that while grading its alerts, and the table then read 186 rows in KQL and zero everywhere downstream — for two sessions. Five hypotheses were formed and five refuted before the answer turned out to be a single availability toggle.
Read a progress indicator twice, spaced. The mirror pane said 99%, 171.6 KB pending, which reads like "catching up". The identical reading five hours later proved it was jammed. One reading is a snapshot; two are a derivative, and only the derivative tells you whether something is slow or stuck.
Load measures over XMLA rather than clicking them in
Twenty-four measures went in as one transaction in 0.7 seconds, with their format strings, against a connection the modelling tools drive directly. Then read every measure back against its rendered value — which is how this build found that its semantic model had no relationships at all. Two visuals were rendering a constant numerator over a varying denominator, and the engine linter, Microsoft's own report validator and a 19-of-19 measure projection check had all passed it. None of them asks whether the model can join. Only a query does.
A Direct Lake model whose auto-update the service disables returns BLANK, not an error
You will get a report full of empty visuals and no message anywhere. Read the setting; do not assume it. It can also come back on by itself.
9

Grade the alerts — the part that makes this a platform rather than a demo

about 3 h

Detection is the easy half. The build is only interesting because it then answers "were those alerts any good?" — against the 137 planted episodes and against the disputes that arrive 30 to 60 days later.

Dispute lag is the whole design problem. An alert raised yesterday cannot be graded yet, because the chargeback that would confirm it has not arrived. A precision figure computed over alerts younger than the lag is not a low precision figure — it is an ungraded one, and publishing it as though it were the first is the single easiest way to lie with this data.

So every alert carries a maturity cohort, and precision is reported per cohort, never blended. The report's headline measure is blank until you slice it to a graded cohort.

// Precision (Reportable) -- deliberately BLANK unless the filter context is a
// single graded cohort. A non-blank unfiltered value is a failure, not a bonus.
Precision (Reportable) =
IF ( HASONEVALUE ( alerts[maturity_cohort] ) && SELECTEDVALUE ( alerts[is_graded] ) = TRUE (),
     DIVIDE ( [True Positives], [Alerts Graded] ) )
Enforce the guard structurally, not by review. This project ships a guarded_measures.json sidecar declaring which measures are the unguarded sources, and a lint rule that fails the build if any visual binds one. The two unguarded precision measures are bound by zero visuals, and a check proves it on every run rather than a reviewer remembering.
Refuse a circular measurement out loud. Reflex 2 graded at a precision of 1.000 — and it had to, because the alert set had been constructed from the very episode it was being graded against. That number is recorded as inadmissible and never rendered. A precision of 1.000 is the shape a too-permissive matcher produces just as readily as a genuinely precise detector, so it is not accepted on plausibility.
Every precision number needs a control that could have refuted it, run before the number is read. Reflex 3's grading was gated on a shifted-window control — the same matcher run against windows deliberately moved 180 days off — returning 0. It did. Only then was the real figure looked at: precision 0.163, recall 60 of 60. And a threshold sweep at 20/30/45 minutes then refuted the project's own explanation for the false positives, which is recorded rather than quietly dropped.

What this build does not do

Stated plainly, so nothing here oversells itself. A reviewer would find all of these in ten minutes; it is cheaper to say them.

  • The two Eventstreams were never built. They are mandatory in this project's own contract, they do not exist in the workspace, and the component count finished at 10 of 11. The backfill route is proven end to end; the live-replay route has working code and nothing to replay into. It is recorded as a degradation rather than reinterpreted as a success, because the alternative is the kind of portfolio piece that quietly redefines its own scope.
  • Reflex 2's precision of 1.000 is inadmissible, and is published as inadmissible. The alert set was constructed from the episode it is graded against.
  • Reflex 3's precision is 0.163, with recall 60 of 60. The false positives are long silences inside modelled trading hours, which points at the trading-calendar model rather than the threshold — a threshold sweep refuted the original explanation. That diagnosis is untested and is labelled as such.
  • The data is invented. Meridian Pay is fictional. The shape is realistic; no figure represents a real company, and every injected element is declared in the repository.
  • Trial capacity only. Nothing here says what this would cost to run in production, and the capacity was shared with another workspace throughout.
  • One data-quality anomaly was never closed — a shortfall of 2 rows against an expected 8,233. It was raised in session three and carried, unexplained, to the end. An open question, never a pass.
If you build this and get further than I did — particularly on the Eventstreams, or on the trading-calendar diagnosis — I would genuinely like to hear about it.
